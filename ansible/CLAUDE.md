# ansible/ — configuration & service deployment

Progressive-disclosure guide for agents working under `ansible/`. Roles
configure services on already-provisioned hosts; Terraform creates the hosts.
The inventory is **generated** — never hand-edit it.

## Layout

```
ansible.cfg              SSH ProxyCommand through the dev-container forward proxy
inventory/
  hosts.yml              GENERATED by scripts/generate-configs.py — DO NOT EDIT
  group_vars/
    all/                 shared vars + secrets template (vault.yml.example)
    pki_root_ca/         GENERATED (root CA name)
    pki_issuing_ca/      GENERATED (issuing CA name/DNS)
roles/                   one dir per service (see table)
playbooks/               one *-setup.yml per service phase + site.yml
```

## Role → service routing

| Role | Configures |
|---|---|
| `common` | base packages, apt source selection, CA trust, `/etc/hosts` mesh, auth-log forwarding (runs first on every host) |
| `step_ca_root` / `step_ca_issuing` / `step_ca_common` | two-tier internal CA (offline root, online issuing) |
| `step_client` | installs the cert client + renewal on any host that requests certs |
| `pdns_auth_recursor` | authoritative DNS + recursor |
| `pdns_dnsdist` | DNS front-end / load balancer + query-log tap |
| `dns_collector` | turns DNS taps into syslog and forwards to the log server |
| `minio` | S3-compatible object store (Terraform state backend + log archive) |
| `nexus` | artifact / apt caching proxy |
| `otelcol` | log collector on the log server (sinks to object store; optional HEC) |
| `splunk` | log analytics (deprecation-planned — prefer the syslog/object-store path) |

Playbooks map 1:1 to phases: `pki-setup.yml`, `dns-setup.yml`,
`dns-dist-setup.yml`, `minio-setup.yml`, `nexus-setup.yml`,
`log-server-setup.yml`, `splunk-setup.yml`; `site.yml` ties them together.

## How to add a host

Hosts are **not** added here. Add the service (or an ad-hoc `hosts:` entry) to
`config/<env>.yml`, then `make configure`. The generator auto-derives the
inventory group, `ansible_host`, and any group vars. See
`scripts/genconfig/CLAUDE.md` and `.claude/rules/config-management.md`. Editing
`inventory/hosts.yml` directly is prohibited — it is overwritten on next run.

## How to add a role

1. `roles/<name>/` with the standard `tasks/`, `defaults/`, `handlers/`,
   `templates/` layout. Prefix every role-owned variable with the role name
   (`<name>_*`) so it can't collide with or shadow shared `all.vars`.
2. Add a `<name>-setup.yml` playbook (or a play in an existing one) and wire it
   into `site.yml`.
3. If the role needs a host, that host comes from a config service (above), not
   a hand-edited inventory.
4. Research the target tool's **native** patterns — don't copy another role's
   structure blindly; adjacent roles are reference points, not templates.

## Convention: apt via the caching proxy

`common` selects apt sources by **probing the proxy's reachability**, not merely
whether one is configured:

- A shared, un-prefixed `nexus_apt_proxy` (base URL) is emitted into `all.vars`
  by the generator. Roles build per-repo URLs from it
  (`{{ nexus_apt_proxy }}/repository/<repo>/`).
- `common` probes the proxy's status endpoint with retries. If reachable it
  deploys proxied DEB822 sources + read-only credentials (looked up from the
  environment) and removes upstream/default sources; if unreachable it falls
  back to the upstream mirror.
- `nexus_fallback` (also a shared `all.vars` var, default **`fail`**) decides
  what an *unreachable-but-configured* proxy means: `fail` aborts with a clear
  message (correct in a firewalled steady state, where there is no usable
  upstream); cold-bootstrap tooling overrides `-e nexus_fallback=upstream`
  because the proxy doesn't exist yet at the first phase. The task layer guards
  with `| default('fail')` as the fail-safe floor. See
  `docs/design/apt-fallback-policy.md`.
- Both `nexus_apt_proxy` and `nexus_fallback` live in `all.vars`, never a role
  default (a role default would mis-prefix and shadow the shared value).

## Convention: internal cert issuance

A two-tier internal CA issues all service certs. The pattern:

- The **offline root** signs the **online issuing CA**; everything else gets
  certs from the issuing CA. `step_client` installs the cert client + automated
  renewal on any host that serves TLS.
- CA trust is bootstrapped by `common` **before** any HTTPS apt runs: it copies
  the root cert into the system trust store and flushes handlers, so the HTTPS
  chain to the caching proxy validates. On a cold start (no root cert on the
  controller yet) it skips trust setup and apt falls back to the upstream
  mirror.
- Services resolve `ca.<domain>` (and other internal FQDNs) via the
  generator-emitted `/etc/hosts` mesh (`common_internal_hosts`), so TLS works
  before the internal DNS server exists. CA URLs are domain-based
  (`https://ca.<domain>`), never IP-based — the CA cert carries only DNS SANs.

## Convention: env-var secret lookups

Secrets are **never** in config YAML, role defaults, or the inventory. They live
only in `.envrc` (generated with `CHANGE_ME` placeholders the operator fills).
Roles read them at runtime via `lookup('env', 'VAR_NAME')` and guard on
non-empty before acting (e.g. the proxy credential file is written only when the
reader password is set). To add a new secret: add the `export VAR="CHANGE_ME"`
line to the `.envrc` emitter and register the name in the generator's secret
list, then consume it via `lookup('env', ...)`. See the secret-boundary table in
`.claude/rules/config-management.md`.

## Convention: syslog forwarding

Host and service logs converge on the log server over syslog:

- `common` forwards host **auth** events via rsyslog to
  `common_log_server_address` (emitted into `all.vars` only when a log server is
  enabled); it also forwards journald to syslog. The auth syslog port is a role
  default.
- The DNS front-end taps query logs; `dns_collector` reshapes them to syslog and
  forwards to `dns_collector_syslog_endpoint` (the log-server IP, auto-wired by
  the generator on the DNS-dist group when a log server is present).
- On the log server, `otelcol` receives the syslog streams and sinks them to the
  object store (primary) with an optional analytics HEC exporter (enabled only
  when that service is enabled).
- Syslog ports are currently duplicated across role defaults rather than emitted
  from one config field (a known low-priority cleanup) — keep them consistent if
  you touch them.

## Workflow

Use the `/ansible-deploy` (full pipeline) or `/ansible-run` (code already
written) skills. Pre-flight: verify every CLI flag a role uses against the
target host's installed version — static review misses version-specific
behaviour. Roles are for **fresh deployment**; one-off cleanup of live-host
state is done manually, not baked into a role.
