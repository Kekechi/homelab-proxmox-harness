# terraform/ — infrastructure provisioning

Progressive-disclosure guide for agents working under `terraform/`. Terraform
creates the VMs/LXCs/networks; Ansible (see `ansible/CLAUDE.md`) configures
them. The `<env>.tfvars` files are **generated** — never hand-edit them.

## Layout

```
main.tf          provider block + one module call per resource (count-gated)
variables.tf     unified variable set (sandbox is the superset)
versions.tf      required Terraform + provider pins
backend.tf       S3 backend (object store); state bucket passed at init time
outputs.tf       resource outputs
<env>.tfvars     GENERATED by scripts/generate-configs.py — DO NOT EDIT
modules/
  proxmox-vm/      a VM (e.g. offline root CA, log-analytics host)
  proxmox-lxc/     an LXC container (most services)
  proxmox-network/ a bridged network / VNet
```

## main.tf → resource routing

Each service is a `module` call in `main.tf`, gated by `count = var.enable_<svc>
? 1 : 0` so a phase is unlocked only when its `enabled` flag is set in config.
Modules are sourced from `modules/` (VM, LXC, or network). Every call passes
`pool_id = var.pool_id` so resources land in the sandbox pool — this is a hard
isolation rule, not a style choice.

## How to add a host

1. Add the service to `config/<env>.yml` (ip, node, network, ids), then
   `make configure` — this regenerates `<env>.tfvars` with the new variables.
2. Add an `enable_<svc>` deployment-gate variable and the per-resource variables
   to `variables.tf`, and emit them from the generator
   (`scripts/genconfig/emit/tfvars.py`).
3. Add the `module` call to `main.tf`, `count`-gated on `enable_<svc>`, with
   `pool_id = var.pool_id` and the network bridge/gateway resolved from the
   service's `network:`.
4. Keep generator emission and Terraform variables in parity — verify both
   layers in review; a value emitted but undeclared (or vice versa) breaks plan.

## How to add a module

Put it under `modules/<name>/` with its own `variables.tf` / `main.tf` /
`outputs.tf`. Follow the `bpg/proxmox` authoring patterns (resource names,
required arguments, cloud-init, network tagging, pool scoping) — see the `proxmox-module`
skill rather than reverse-engineering an existing module. Never set tags on any
VM or LXC. Verify provider/resource behaviour against the official provider docs
before asserting how an argument behaves.

## Convention: apt via the caching proxy

Terraform itself doesn't consume the proxy — package installation happens in
Ansible (see `ansible/CLAUDE.md`). Terraform's role is to inject the resolver
into each host's init block (`dns_servers`) and to place the caching-proxy host
on the right node/network so it's reachable once Ansible runs.

## Convention: internal cert issuance

Terraform provisions the CA hosts but does not issue certs. The **offline root**
is a VM deliberately created stopped (not started, not start-on-boot) — it boots
only to sign or rotate. The **online issuing CA** is an always-on LXC fronted by
a TLS stream proxy. Cert issuance and trust bootstrapping are Ansible's job
(`step_*` roles). Bootstrap note: a one-time host-side template-creation step
must run before the first apply for the VM-based services.

## Convention: env-var secret lookups

No credentials in `.tf` files — ever. The provider block reads the API
endpoint, token, and TLS-skip flag from environment variables (populated from
`.envrc`, which the generator writes with `CHANGE_ME` placeholders the operator
fills). The S3 state backend likewise reads its keys from the environment, and
when the backend is TLS-fronted, the CA-bundle env var points the S3 client at
the exported internal root cert. To add a secret, add it to the `.envrc` emitter
and consume it via an env var — never as a `variable` default or hardcoded
literal. See the secret-boundary table in `.claude/rules/config-management.md`.

## Convention: syslog forwarding

Not a Terraform concern — the syslog pipeline is configured by Ansible (`common`
+ `dns_collector` + `otelcol`; see `ansible/CLAUDE.md`). Terraform's only part
is placing the log-server host and ensuring its network reaches the log sources.

## Workflow (hard rules)

- **Never** `apply` without a plan file: `plan -out=<file>` first.
- **Never** apply production — generate a plan and hand it to the operator
  (`/handoff`). The production token is intentionally absent from the dev
  container.
- Switch env with `ENV=` (`make plan ENV=production`).
- Never hardcode credentials/IPs; never `-target` a partial apply, run
  `state mv/rm`/`import`, or `force-unlock` without explicit operator approval.

Use the `/tf-deploy` (full pipeline) or `/infra-plan` → `/generate` → `/review`
skills. Full init/plan/apply detail: the `tf-plan-apply` skill.
